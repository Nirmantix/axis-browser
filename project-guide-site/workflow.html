The workflow: observe, act, prove.

Start with the rendered browser. Let Axis launch and own it, capture real state, then choose whether the task needs quick diagnostics, audited evidence, or a rerunnable script.

Browser debugging

Use this for web apps, desktop apps with webviews, SaaS dashboards, internal tools, auth flows, and anything where real browser state matters.

# Axis launches and owns the browser. No port to manage.
axis-browser open http://localhost:3000
axis-browser snapshot
axis-browser console --type error
axis-browser network --type fetch
Reproduce

Open the exact route or tab where the issue exists. Use the same login state if auth matters.

Inspect

Snapshot shows accessible structure and @gN:N refs. Console and network show runtime causes.

Interact

Click or fill refs exactly as printed. If stale, re-snapshot and retry.

Decide

Edit app code only after the browser evidence identifies a failing request, exception, or state mismatch.

Persistent-login baseline

When a task needs a logged-in session, use managed mode: Axis launches and owns a Chrome on a profile that persists between runs, so you sign in once. Launch modes drive the browser over a pipe — there is no debugging port to manage or collide with. Only the local Axis bridge uses a port (9224).

export CHROME_DEVTOOLS_AXI_MODE=managed   # profile: ~/.axis-browser-data

axis-browser login https://app.example.com # one-time, interactive
axis-browser open https://app.example.com  # silent from here on
axis-browser snapshot
Dedicated profile

~/.axis-browser-data keeps automation login state separate from the everyday browser profile.

Bridge reset

axis-browser stop clears the persistent bridge so the next command uses the current environment and target.

Generation-tagged refs

Refs such as @g1:3 must be passed back exactly as printed. STALE_REF means the page changed and a new snapshot is required.

Stop-guessing debug protocol

  1. 1
    Reproduce in the browser

    Open the target route or tab in the controlled shared browser session.

  2. 2
    Capture structure

    Run axis-browser snapshot and inspect the visible accessible state.

  3. 3
    Inspect runtime failures

    Run axis-browser console and axis-browser network before editing application code.

  4. 4
    Identify the concrete failure

    Look for the failing request, exception, disabled control, missing DOM state, or auth/session mismatch.

  5. 5
    Change code only after evidence

    Use browser observations to drive the implementation fix or the verified-run report.

Auth, tabs, and ports

Situation Operational pattern Command or note
Normal login state Run the one-time interactive login on the managed profile; every later run reuses it silently. axis-browser login <url>
SSO, MFA, or sensitive providers The managed profile is an ordinary Chrome profile on disk and no debugging port is involved, so sign in through login and the session persists like normal browsing. ~/.axis-browser-data
Named sessions start logged out Chrome locks a profile to one process, so each named session gets its own (<dir>/sessions/<name>). Doctor reports this as NEEDS_INTERACTIVE_LOGIN. axis-browser doctor --json
Your real browser profile Refused outright. Chrome silently declines to bind a debugging socket on a default profile, and automation would fight your own browser for the lock. Use a dedicated directory.
Tab source of truth Ask the tool — launch modes expose no TCP endpoint to probe by hand. axis-browser pages
Axis bridge port Default is 9224. Change only when the local Axis bridge port conflicts. CHROME_DEVTOOLS_AXI_PORT=9225

Troubleshooting

Start with axis-browser doctor --json. It names the active mode, probes the endpoint, reports the profile and bridge state, and prints remedies that are syntactically runnable commands — which is not the same as safe to run unattended. Run the reversible ones (unset …) directly; confirm the destructive ones (axis-browser reap, axis-browser stop, rm <path>) with a human first. Escalate to a human outright only for NEEDS_INTERACTIVE_LOGIN or PORT_HELD_BY_FOREIGN_PROCESS. Local CDP has no authentication — never request credentials, tokens, or a ws:// URL.

Bridge feels stale

  • reset axis-browser stop
  • check axis-browser pages
  • note Deep health checks recycle most stale bridge states automatically.

Bridge startup is slow

  • fast Default stdio mode launches the pinned package-local chrome-devtools-mcp@1.9.0 — no global install is used or detected. Only an explicit CHROME_DEVTOOLS_AXI_MCP_PATH override changes the executable; reinstalling some unrelated global copy changes nothing.
  • timeout CHROME_DEVTOOLS_AXI_BRIDGE_TIMEOUT_MS=60000

Bridges accumulating

  • check axis-browser reap --dry-run
  • clean axis-browser reap
  • cause A bridge lost to SIGKILL or a crash never runs its own cleanup and leaks a process group holding an invisible browser.

Login state is missing

  • mode Confirm managed — ephemeral has no profile at all.
  • session A named session has its own profile and starts logged out.
  • fix axis-browser login <url>

Verified run workflow

Use this when an operator, reviewer, or future agent needs checkable proof instead of a verbal claim.

# Resolve the skill directory first. Unset BROWSER_BAY_DIR would
# otherwise run node "/scripts/..." and fail with a confusing path error.
BB=""
c="${BROWSER_BAY_DIR:-${BROWSER_SKILL_DIR:-}}"
[ -n "$c" ] && [ -d "$c" ] && BB="$c"
for p in "${AXIS_BROWSER_HOME:+$AXIS_BROWSER_HOME/skills}" "${AXIS_PORTABLE_SKILLS_DIR:-}" \
         ./skills "$HOME/.codex/skills" "$HOME/.config/agents/skills" \
         "$HOME/.claude/skills" "$HOME/.config/opencode/skills" \
         "$HOME/.pi/agent/skills" "$HOME/.agents/skills" \
         "$HOME/.cursor/skills" "$HOME/.kiro/skills" "$HOME/.gemini/skills"; do
  [ -n "$BB" ] && break
  [ -n "$p" ] || continue
  for n in browser-bay browser-skill; do
    if [ -d "$p/$n" ]; then BB="$p/$n"; break; fi
  done
done
[ -d "$BB" ] || { echo "browser-bay not found; set BROWSER_BAY_DIR"; exit 2; }


# Scaffold a single-pass evidence bundle.
node "$BB/scripts/init-verified-run.mjs" \
  --task "Verify checkout renders an order confirmation" \
  --slug checkout-confirmation

# After filling plan.md and findings.md, validate it.
node "$BB/scripts/validate-verified-run.mjs" \
  --run .tmp/verified-runs/checkout-confirmation
Exit Status Operator action
0 pass All checks have valid PASS markers. Report the run and evidence.
1 fail:structure Fix malformed artifacts, missing markers, invalid IDs, or unsafe screenshot paths.
2 fail:checks Checks are structurally valid but failed or skipped. Report honestly or iterate.

Reusable workflow craft path

Use this when the deliverable is a browser workflow someone can rerun with different inputs.

Start craft mode

Craft mode changes the scaffold instructions. It does not magically generate automation.

BB=""
c="${BROWSER_BAY_DIR:-${BROWSER_SKILL_DIR:-}}"
[ -n "$c" ] && [ -d "$c" ] && BB="$c"
for p in "${AXIS_BROWSER_HOME:+$AXIS_BROWSER_HOME/skills}" "${AXIS_PORTABLE_SKILLS_DIR:-}" \
         ./skills "$HOME/.codex/skills" "$HOME/.config/agents/skills" \
         "$HOME/.claude/skills" "$HOME/.config/opencode/skills" \
         "$HOME/.pi/agent/skills" "$HOME/.agents/skills" \

  [ -n "$BB" ] && break

node "$BB/scripts/init-verified-run.mjs" \

  --slug flight-search \
  --mode craft
Prove once

Use Axis Browser, Browser Harness, or Playwright to complete the flow and collect evidence.

Refactor

Turn the working flow into script.mjs with explicit flags and defaults from task.md.

Prefer Playwright

For deterministic multi-page scripts, Playwright is the safer default backend.

Validate

Run the verified-run validator and report PASS, FAIL, or SKIP markers.
